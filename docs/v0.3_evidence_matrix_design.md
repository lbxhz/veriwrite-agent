# V0.3：全文证据卡与文献矩阵

## 一句话目标

V0.3把V0.2确认的“真实论文列表”转化为“每个结论都能定位到PDF页码和原文片段的
确认版证据库”，供后续大纲与写作模块消费。

这一步不负责写课程论文。它只回答三个问题：

1. 论文PDF是否成功取得并对应正确DOI？
2. 系统总结的研究对象、数据、方法、结果和局限，分别由哪一页原文支持？
3. 多篇论文在相同维度上如何比较？

## MVP工作流

```text
V0.2 SelectedLiteratureRecord
  -> 用户选择少量核心论文
  -> Agent打开DOI权威入口并建立下载队列
  -> 用户只处理登录、验证码与出版社下载按钮
  -> Agent扫描下载目录，按DOI/题名自动匹配PDF
  -> 检查文件头、EOF、页数、可提取文本、SHA-256与论文身份
  -> 缺失项保留为upload_required，可在下载后断点继续
  -> 非核心论文保留为metadata_only，不冒充全文已验证
  -> 原生文本提取；扫描页走OCR
  -> 保留PDF页码，生成DocumentPage
  -> LLM从指定页面文本生成EvidenceCard草案
  -> 确定性代码检查引文确实存在于对应页和对应文件
  -> 按研究对象、数据、方法、结果、局限生成LiteratureMatrix
  -> 用户集中确认关键证据卡
  -> Confirmed EvidenceLibrary
  -> 根据证据覆盖微调并确认WritingOutline
  -> V04WritingHandoff
```

## 核心数据合同

### `DocumentAcquisition`

保存PDF取得状态、取得方式、URL、本地路径、文件哈希、尝试次数和失败原因。
`upload_required`是正常降级，不等于整个Agent故障。

### `PdfInspectionBatch`

保存一次下载目录扫描的核心论文队列、匹配结果、完整性问题和缺失项。
`verified`只表示PDF身份与文件完整性已经由确定性规则确认；
`needs_review`用于可打开但需要OCR或人工复核的文件，不能静默进入证据提取。

### `DocumentPage`

保存某个DOI、某个PDF哈希、某一页的文本及提取方式。页码必须来自PDF分页，
不能使用LLM自行估计的页码。

### `EvidenceCard`

保存LLM规范化后的结论、证据类型、主题、支持强度，以及1—3段短原文。
没有原文片段就不能生成证据卡。

### `LiteratureMatrixRow`

按研究对象、数据来源、方法、主要发现和局限横向整理论文。矩阵每个非空单元格都必须
引用`evidence_card_ids`，不能出现没有证据来源的总结。

### `LiteratureLibraryRecord`

把全部V0.2入选文献分为两个可信层级：

- `A_core/full_text_verified`：已核对并读取PDF，可在二次精读后承担详细结论；
- `B_supporting`或`C_background/metadata_verified`：只确认RIS、官网元数据或摘要，
  不能支持具体数值、实验设计和强结论。

### `V04WritingHandoff`

V0.4只接受三个已确认合同：`ConfirmedRequirementSpec`、
`ConfirmedWritingOutline`和`Confirmed EvidenceLibrary`。任一PDF、证据卡或章节
覆盖缺口存在时，交接合同不能生成。

## 代码与LLM的边界

| 工作 | 执行者 | 原因 |
|---|---|---|
| 核心论文选择与下载排队 | Agent + 用户 | Agent减少操作，用户处理权限与验证码 |
| PDF匹配、哈希、文件类型、页码 | 确定性代码 | 属于可验证事实 |
| PDF文本提取与OCR路由 | 确定性代码 | 需要稳定、可测试 |
| 判断句子属于方法、结果还是局限 | LLM | 需要语义理解 |
| 将多段原文规范化为简短结论 | LLM | 需要语言归纳 |
| 检查引文是否存在于对应页 | 确定性代码 | 防止LLM伪造引文 |
| 关键证据取舍 | 用户集中确认 | 会影响后续全文论证 |

`EvidenceGroundingValidator`会在用户确认前检查：

- 页码是否存在；
- 页面是否来自证据卡声明的PDF哈希；
- 引文经Unicode与空白规范化后是否真的存在于该页。

## MVP验收标准

首轮只使用少量核心真实PDF，不追求一次处理全部文献：

1. 用户下载后，正确PDF可自动匹配；缺失论文明确进入`upload_required`；
2. 每篇PDF保存SHA-256，重复运行不得误用其他版本文件；
3. 损坏文件、错误PDF和扫描版PDF必须分别进入`invalid`或`needs_review`；
4. 每篇至少形成研究对象、方法、主要结果三类证据卡；
5. 100%的证据卡至少包含一个页码和短原文；
6. 人为构造的错误页码、错误文件哈希和虚假引文必须被自动测试拦截；
7. 文献矩阵每个非空单元格都能追溯到同一篇论文的证据卡；
8. 未解决问题存在时，系统不能输出`confirmed`证据库。

## 真实烟雾测试

2026-07-31使用用户下载目录进行测试：

- 识别2篇正确核心PDF；
- 识别1个实际为HTML的人机验证/网页下载结果；
- 识别1篇不属于本次队列的其他论文和1份重复PDF；
- 收紧自动匹配阈值，低于0.8的题名部分匹配不再分配给核心任务；
- 两篇正确PDF分别完成12/12页、13/13页原生文本提取；
- 首页渲染确认题名、期刊、DOI和正文布局可读。

## 与Agent解决方案工程师的关系

V0.3重点不是选择某个PDF库，而是完成解决方案设计中的关键闭环：

- 定义阶段输入、输出与完成条件；
- 给外部工具设计成功、重试、降级和人工接管路径；
- 不把出版社认证和验证码误当成适合完全自动化的问题；
- 限制LLM权限，只让它承担语义任务；
- 用数据合同和确定性验证约束幻觉；
- 保存状态与证据，使长任务可恢复、可解释、可审计；
- 用真实样例和故意失败样例定义评测。

面试中应能说明：这个Agent的价值不是“会总结PDF”，而是能把总结转化为后续模块
可以安全消费的、逐条可追溯的证据资产。
