# V0.1 科普：从要求原文到确认版数据合同

这份说明面向 Agent 解决方案工程师。重点不是记住每个 Python 类，而是能回答五个问题：

1. 客户原始要求为什么不能直接交给写作 Agent？
2. 每个组件解决什么风险？
3. LLM、确定性代码和用户分别负责什么？
4. 一个阶段怎样证明已经完成？
5. V0.1 怎样安全地把状态交给 V0.2？

## 1. RequirementSpec：统一的数据合同

可以把 `RequirementSpec` 理解为一张有固定栏位的海关申报表。

自然语言可以写成“至少一万五千字”“1.5 万字以上”或“篇幅不得少于 15000 字”，但进入系统后都必须放到同一个字段：

```text
length.minimum_chars = 15000
```

数据合同规定：

- 系统允许保存哪些字段；
- 每个字段是什么类型；
- 数字允许处于什么范围；
- 字段之间有哪些关系；
- 出现未知字段或非法值时必须拒绝。

Pydantic 是实现合同检查的工具，`RequirementSpec` 才是业务合同本身。后续 V0.2、V0.3 不需要重新阅读课程原文，只消费用户确认后的结构化合同。

## 2. 规则解析器：稳定、可重复的第一位检查员

`RuleBasedRequirementParser` 使用正则表达式和明确规则提取字数、参考文献数量、比例和格式。

它的优势是：

- 相同输入必然得到相同输出；
- 不需要 API Key 和模型费用；
- 数字和比例的行为容易测试；
- 可以作为 LLM 解析结果的基线。

它的局限是无法理解大量没有预先编写规则的语义表达。因此规则解析器不是为了替代 LLM，而是负责自己更擅长的硬约束。

## 3. 双路解析：让两位能力不同的检查员独立工作

双路解析不是把规则结果交给 LLM 修改，而是让两者阅读同一份原文并独立输出同一个 `RequirementSpec`：

```text
原始要求 ──> 规则解析器 ──> 候选 A
       └──> LLM 解析器  ──> 候选 B
```

这样才能发现：

- 规则遗漏了语义要求；
- LLM 遗漏了数字约束；
- LLM 猜测了原文中不存在的内容；
- 两条路径对同一字段理解不同。

如果先把一方结果告诉另一方，就容易产生锚定效应，失去独立交叉检查的价值。

## 4. RequirementReconciler：确定性合并器

合并器不是第三位自由发挥的 LLM，而是一套可以解释和重复执行的裁决规则：

1. 两边相同：自动接受；
2. 一边为空、一边有合法值：保留已知值；
3. 两边都有值且不同：生成 `RequirementConflict`；
4. 新值会破坏数据合同时：拒绝自动合并并记录冲突；
5. 冲突暂时保留规则值，但必须由用户最终决定；
6. 原始候选、冲突和来源证据都保留，不能覆盖历史。

例如：

```text
规则结果：minimum_chars = 15000
LLM 结果：minimum_chars = 12000
```

系统不会平均成 13500，也不会默认相信 LLM，而是输出：

```text
field = "length.minimum_chars"
rule_value = 15000
llm_value = 12000
provisional_value = 15000
status = 等待用户确认
```

## 5. 完整性检查：判断能否进入下一阶段

“通过 Pydantic”只表示数据结构合法，不代表业务信息完整。

例如下面的数据在类型上合法，但无法开始文献检索：

```text
topic = null
```

因此 `RequirementCompletenessChecker` 还要检查：

- 研究主题是否确认；
- 是否还有解析冲突；
- 字数和文献数量是否缺失；
- 字数统计口径是否待确认；
- 参考文献著录标准是否待确认；
- 原文歧义是否已向用户展示。

问题分为两类：

- `blocking`：不解决就不能进入 V0.2；
- `warning`：可以保留为已知风险，但必须展示或确认。

## 6. 用户确认：Human-in-the-loop 控制点

用户确认不是点击一个没有信息的“同意”按钮。系统向用户展示：

- 合并后的临时结果；
- 规则和 LLM 的原始候选；
- 每一项冲突；
- 缺失信息；
- 仍待确认的假设。

用户通过字段更新解决阻塞项，并明确确认其余警告。所有更新再次经过 `RequirementSpec` 校验。

最终输出 `ConfirmedRequirementSpec`，其中包括：

```text
status = confirmed
confirmed_by
confirmed_at
requirement
acknowledged_issue_ids
remaining_warnings
```

这份确认版本才是 V0.2 的正式输入。

## 7. V0.1 完整工作流

```text
TXT / Markdown / DOCX
→ 提取文本
→ 规则与 LLM 独立解析
→ 两边分别通过 RequirementSpec 校验
→ RequirementReconciler 确定性合并
→ RequirementCompletenessChecker 生成检查表
→ 输出 requirement_review.json
→ 用户修正冲突、补充主题并确认警告
→ RequirementSpec 再校验
→ 输出 confirmed_requirement_spec.json
```

旧版 `.doc` 不是开放 XML 格式，V0.1 要求先转换为 `.docx`，避免在需求解析器中引入不稳定的格式兼容逻辑。

## 8. 版本与 MVP 的关系

正确关系不是“分别完成几个孤岛，最后一次性拼接”，而是逐层扩展同一条状态流：

```text
V0.1 确认要求
  ↓ confirmed_requirement_spec.json
V0.2 检索并验证文献身份
  ↓ verified_references
V0.3 建立全文证据卡
  ↓ evidence_cards
V0.4 大纲和分章节写作
  ↓ draft_sections
V0.5 综合审计和导出
  ↓ MVP
```

每个版本都应满足三个条件：

1. 自己可以运行和验收；
2. 输出是下一版本的正式数据合同；
3. 失败、冲突和人工决定可以追溯。

当 V0.1 到 V0.5 串成一条最小但完整的用户价值链时，形成 MVP。MVP 验证用户是否真正需要这套方案；之后再优化界面、性能、模型选择、自动化比例和企业集成。

## 9. 解决方案工程师应该怎样表达

推荐表达：

> 原始课程文件是非结构化输入，直接交给写作模型会产生约束遗漏和不可追溯修改。V0.1 通过统一数据合同、规则与 LLM 双路提取、确定性合并、完整性检查和用户确认，把模糊要求转成可供后续模块稳定消费的确认状态。我的重点不是让模型多调用一次，而是设计信任边界、异常路径、人工控制点和可验收的阶段交付。

不需要把重点放在正则表达式怎样编写或类有多少方法；需要能解释组件为什么存在、解决什么风险、输入输出是什么，以及失败时系统如何处理。
