# V0.1 学习笔记：成熟 Agent 的地基

## 1. Agent 不等于一次 LLM 调用

可以先使用这个心智模型：

```text
Agent = 模型 + 工具 + 状态 + 决策规则 + 反馈循环 + 评测
```

V0.1 先实现“状态、规则和评测”。后续接入 LLM 时，模型只能在系统允许的范围内填写结构化对象，不能随意创造字段或绕过验证。

## 2. 为什么先定义 Pydantic 模型

普通 Python 字典可以随意缺字段、拼错字段或写入错误类型。Pydantic 模型相当于系统的数据合同：

- `minimum_total` 必须是正整数；
- `minimum_foreign_ratio` 必须在 0 到 1 之间；
- `max_references_per_citation_cluster` 不能小于 1；
- 解析器、数据库、API 和测试共享同一份定义。

当数据不符合合同时，程序应立即报错，而不是把错误传递到写作阶段。

## 3. 为什么 V0.1 先用规则解析器

规则解析器能力有限，但有三个优点：

1. 相同输入必然得到相同输出；
2. 不需要 API Key 和模型费用；
3. 能成为后续 LLM 解析器的基线。

后续不会删除规则解析器。成熟方案通常会让规则负责数字、比例和格式，让 LLM 负责主题、范围、隐含意图和歧义解释。

## 4. 代码目录分别承担什么责任

- `models/`：定义“什么数据是合法的”；
- `services/`：完成一个明确的业务动作；
- `cli.py`：把业务动作暴露给人或脚本调用；
- `tests/`：把需求变成机器可以反复执行的验收标准；
- `fixtures/`：保存固定输入，防止每次测试使用不同样例；
- `docs/`：记录为什么这样设计，方便面试讲解和团队协作。

## 5. Git 的四个核心概念

- 工作区：你当前看到并修改的文件；
- 暂存区：你准备放入下一次版本记录的文件；
- 提交：一个带说明的项目快照；
- 仓库：保存全部提交历史的目录。

最常用的第一组命令：

```powershell
git status
git add .
git commit -m "feat: build V0.1 requirement parser"
git log --oneline
```

不要把 `.env`、API Key、虚拟环境和运行时输出提交到 Git；这些内容已经写入 `.gitignore`。

## 6. 本阶段面试表达

可以这样描述 V0.1：

> 我没有直接让 LLM 开始写论文，而是先定义课程要求的数据合同，并用确定性解析器和自动化测试建立基线。这样后续即使更换模型，系统仍能检查字数、参考文献数量、外文比例、引用聚合上限和歧义，不依赖聊天上下文记忆。
