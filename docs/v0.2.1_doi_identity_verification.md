# V0.2.1 DOI 与元数据身份验证

## 原始 DOI 从哪里来

原始 DOI 来自 V0.2.0 `CrossrefSearchProvider`返回的`LiteratureCandidate.doi`。
LLM 只负责生成检索关键词，不生成、补写或修改 DOI。Crossref 候选缺少合法 DOI 时，
它不会进入`LiteratureCandidate`。

## 验证链路

```text
Crossref LiteratureCandidate
  -> 使用候选 DOI 通过 DOI Content Negotiation 请求 Crossref RIS
  -> 保存注册机构返回的原始 RIS
  -> 检查 RIS 的 DOI、题名、作者、年份、期刊是否完整
  -> 检查 RIS DOI 是否等于请求的候选 DOI
  -> 使用 https://doi.org/{RIS DOI} 解析
  -> 保存最终落地 URL 和 HTTP 状态
  -> VERIFIED 或 EXCLUDED
```

普通 DOI 请求由 DOI Proxy 重定向到登记的资源地址。带
`Accept: application/x-research-info-systems`的请求通常转到 DOI 注册机构的元数据服务；
对 Crossref DOI，实际 RIS 来源通常是 Crossref transform 接口。

## 通过条件

Crossref RIS 是 V0.2.1 的基准文献记录。只有同时满足以下条件才返回`verified`：

- DOI 注册机构能够返回合法的单条 RIS；
- DOI、题名、作者、年份、期刊五项信息完整；
- RIS 的`DO`字段等于请求的候选 DOI；
- RIS DOI 能解析到最终落地地址；若出版社拒绝自动访问，但已发生重定向，则保留访问警告。

任何条件不满足都返回`excluded`，并保存原因，例如：

- `doi_unresolvable`
- `landing_page_unavailable`（警告，不等同于虚假 DOI）
- `authority_metadata_invalid`
- `authority_missing_authors`
- `ris_doi_mismatch`

网络错误最多尝试三次。三次后仍不可用时记录`unavailable`，不会伪装成 DOI 不存在，
也不会进入可信文献库。

出版社对自动化客户端返回 403 等状态时，说明页面访问受限，不等于 DOI 不存在。系统仍会
尝试获取注册机构 RIS；如果 RIS 完整且身份字段一致，可以进入`verified`，同时保留
`landing_page_unavailable`警告，供后续全文获取阶段处理。

## 证据合同

- `DoiResolutionEvidence`：解析地址、最终地址、HTTP状态、尝试次数和检查时间。
- `AuthoritativeMetadataEvidence`：RIS来源地址、RIS原文、解析结果和检查时间。
- `LiteratureVerificationResult`：`verified/excluded`最终决策及原因代码。

这些对象以后可以直接持久化到 SQLite，并由 UI 显示排除原因。

## 当前能力边界

V0.2.1 验证的是“Crossref登记候选是否对应一个可解析 DOI，且注册机构 RIS 是否描述同一
文献”。它不证明论文正文内容正确，也不判断论文是否适合当前主题。

Crossref搜索结果和Crossref注册机构RIS来自同一套出版成员提交的数据，因此不做没有独立
证据价值的题名、作者逐字段重复比较。系统以RIS作为规范记录，DOI落地解析提供第二个
可解析性信号。若以后需要更强验证，应比较出版社页面`citation_*`结构化元数据与RIS。

## 真实冒烟测试

真实候选`10.5638/thagis.33.si-22`的测试结果：

- DOI 最终跳转到 J-STAGE 论文页面；
- DOI 内容协商返回 Crossref RIS；
- DOI、题名、年份和期刊精确一致；
- 作者经过姓名顺序规范化后一致；
- 最终状态为`verified`。
