# M0 产品需求文档：可验证的课程研究与写作 Agent

版本：M0（需求定义与基线阶段）  
暂定名称：VeriWrite Agent  
样例来源：中国地质大学未来技术学院硕士学位课程《研究方向文献综述》要求

## 1. 项目目标

构建一个面向课程文献综述的研究与写作 Copilot。系统需要把自然语言或 Word 格式的课程要求转换为结构化任务，检索和验证真实文献，建立“文献—证据—主张”对应关系，并采用分章节方式生成、检查和组装长文。

项目不以“一键代写并直接提交”为目标。最终内容必须经过用户确认，系统需保留来源、证据与修改记录。

## 2. 为什么不能只调用一次 LLM

直接调用 LLM 存在四类核心问题：

1. 长对话中遗漏字数、结构、引用比例和格式等约束；
2. 生成不存在或元数据相互矛盾的文献；
3. 引用真实论文，但论文与主题无关或不支持正文主张；
4. 单次输出无法稳定生成并审查 15000 字以上的长文。

本项目通过结构化需求、持久化状态、确定性文献校验、全文证据卡和分章节生成解决这些问题。

## 3. 目标用户

- 需要完成课程文献综述、研究背景或课程论文的研究生；
- 需要核查学生综述格式与引用质量的导师；
- 希望保留研究过程、文献矩阵和证据链的科研人员。

## 4. 样例课程要求解析结果

### 4.1 交付物

完整提交包包括：

1. 《研究方向文献综述》说明；
2. 研究生课程论文封面；
3. 考试成绩登记表；
4. 文献综述正文；
5. 参考文献列表。

首次提交时，“修改说明”可以为空；学院审核未通过后的再次提交必须填写修改说明。

### 4.2 主题与内容

- 文献类型：研究方向文献综述；
- 必须体现人工智能、新一代信息技术与专业领域的交叉融合；
- 应体现多学科交叉特色；
- 不能逐篇罗列题目或摘要；
- 必须综合、比较、评价文献，并形成作者自己的观点；
- 建议结构包括摘要、引言、国内外研究现状、方法比较、存在问题、技术发展趋势、结语；
- “现状分析”和“亟待解决的问题及设想”属于重点内容。

### 4.3 长度与排版

- 正文字数：至少 15000 字；
- 图件不计入字数；
- 正文：宋体、小四号、1.5 倍行距；
- 纸张：A4；
- 打印：单双面均可。

### 4.4 参考文献

- 文献总数不少于 60 篇；
- 外文文献不少于总数的三分之一；60 篇时至少需要 20 篇外文文献；
- 尽量选用近 5 年国内外重要期刊论文、专著和硕博学位论文；
- 少引用会议论文和报告，除非确实重要；
- 每篇列入参考文献表的文献都必须在正文中被正确引用和评述；
- 引文按正文首次出现顺序编号，采用上角标；
- 单个引用位置一次最多引用 4 篇文献；
- 文内序号与文后列表必须一一对应；
- 参考文献格式必须完整、规范。

### 4.5 公式、表格和图件

- 公式必须可编辑，不能以图片形式复制；
- 首次出现的符号和变量必须解释物理或数学意义；
- 公式居中、编号右对齐，引用他人公式需标注；
- 表格必须重新制作成可编辑三线表；
- 引用的图件必须标注来源；
- 所有表格和图件都必须在正文中分析、解释或说明。

## 5. 发现的歧义与处理策略

1. 文件一处写“15000 字以上”，另一处写“1.5 万字左右”。系统默认采用更严格的“至少 15000 字”。
2. “近 5 年”使用了“尽量”而不是“必须”。系统将其解析为软约束，并在审计报告中计算近 5 年文献比例。
3. 文件未给出 GB/T 7714 等明确著录标准。V0 只记录“顺序编码制 + 上角标”，在正式写作前要求用户或教师确认具体参考文献格式。
4. 文件没有定义“字数”的计算方式。V0 默认统计中文字符与英文单词，排除标题、参考文献和图表题注；正式版本允许切换学校口径。
5. “外文文献”可能按语言、出版地或期刊来源判断。V0 默认按文献主要语言判断，并允许人工修改。

## 6. 核心工作流

1. 读取课程要求与用户补充说明；
2. 生成结构化 RequirementSpec；
3. 向用户展示任务确认单，处理歧义；
4. 根据主题生成检索策略；
5. 从学术数据库获取候选文献；
6. 验证 DOI、标题、作者、年份和来源是否一致；
7. 保存 RIS/BibTeX 与稳定链接；
8. 获取或接收用户上传的核心 PDF；
9. 建立文献矩阵和证据卡；
10. 生成章节大纲和字数预算；
11. 逐章节写作、审查和持久化；
12. 执行要求、引用、证据、结构、字数和风格审计；
13. 输出 Markdown，后续版本输出 Word。

## 7. 文献可信度模型

每篇文献使用以下状态机：

`DISCOVERED -> METADATA_VERIFIED -> RIS_SAVED -> FULLTEXT_READY -> EVIDENCE_EXTRACTED -> CITED -> AUDITED`

### 7.1 元数据验证

只有在以下字段能够指向同一篇文献时，才可进入 `METADATA_VERIFIED`：

- DOI 或其他稳定标识符；
- 标题；
- 作者；
- 年份；
- 期刊、出版社或学位授予机构。

“DOI 能打开”不是通过条件。若 DOI 打开后标题或作者不匹配，记录状态必须为 `REJECTED_IDENTITY_MISMATCH`。

### 7.2 相关性验证

真实存在但与主题无关的文献不得进入正式引用池。系统需要记录：

- 与研究问题的相关性；
- 可支持的章节；
- 可支持的主张；
- 不适合支持的内容。

### 7.3 证据验证

RIS 只能证明元数据来源，不能证明正文主张。具体数据、实验结果、方法细节和结论强度必须来自摘要或全文证据卡。证据卡至少包含：

- 文献 ID；
- 原文片段或忠实释义；
- 页码或章节位置；
- 可支持的主张；
- 证据限制；
- 人工复核状态。

## 8. M0 基线实验

### 8.1 目的

证明“直接把课程要求发送给 LLM”在哪些方面失败，为后续版本提供可量化对照。

### 8.2 基线输入

准备至少 5 份不同写法的课程要求，其中至少包括：

- 当前附件；
- 一份要求英文文献比例的综述；
- 一份带指定章节和字数分配的论文；
- 一份包含表格、公式或图件要求的论文；
- 一份存在冲突或模糊表述的要求。

### 8.3 基线任务

让同一个模型仅依据原始要求完成：

1. 提取课程要求；
2. 给出研究计划；
3. 推荐 20 篇参考文献；
4. 生成一段带引用的样例正文。

### 8.4 评测指标

- Requirement Recall：显性和隐性要求提取召回率；
- Requirement Precision：是否生成文件中不存在的要求；
- Citation Existence：文献是否真实存在；
- Metadata Consistency：DOI、标题、作者、年份是否一致；
- Topical Relevance：文献是否与主题相关；
- Claim Support：引用是否支持正文主张；
- Citation Coverage：需要引用的主张是否包含引用；
- Format Compliance：引用数量、比例、顺序和单处聚合数量是否合规；
- Cost、运行时间和人工修改时间。

## 9. V0.1 功能范围：课程要求解析器

### 9.1 输入

- 纯文本；
- `.docx`；
- 旧版 `.doc` 先转换后解析；
- 用户补充说明。

### 9.2 输出

- `requirement_spec.json`；
- 面向用户的任务确认单；
- 歧义与缺失信息列表；
- 解析依据和来源位置。

### 9.3 验收标准

- 当前样例中的硬约束全部被正确提取；
- 至少识别 5 类软约束；
- 不把“示例题目”误判为用户真实题目；
- 能识别“首次提交”和“审核未通过后再次提交”的条件要求；
- 能发现“15000 字以上”与“1.5 万字左右”的表述差异；
- 未确认的引用格式不得由系统擅自填成 GB/T 7714；
- 输出通过 JSON Schema/Pydantic 校验；
- 每个字段保留来源文本或页码，便于人工核对。

## 10. 非功能要求

- API Key 只能通过环境变量读取，不得写入 Git；
- 所有外部 API 调用必须设置超时、重试、缓存和限速；
- 每次运行保存结构化日志；
- 中间状态可恢复，失败后不必从头运行；
- 验证失败时必须拒绝或标记，不得静默放行；
- 写作模块不得直接创造新的参考文献；
- 风格润色模块不得修改 DOI、数字、公式、引用编号和证据含义。

## 11. 首版技术选择

- Python 3.11+
- Pydantic：需求和文献数据模型
- httpx：API 调用
- SQLite：项目状态和缓存
- pytest：单元测试和回归测试
- Markdown/JSON：第一阶段输出
- Git：从 V0.1 开始进行版本管理

V0.1 暂不引入 LangChain、LangGraph、多 Agent 或向量数据库。先通过普通 Python 函数和清晰的数据模型实现稳定流程。
